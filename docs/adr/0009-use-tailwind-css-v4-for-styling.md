# ADR-0009: Use Tailwind CSS v4 for Styling

## Status

Accepted

## Context

The project needs a styling system that is fast to work in, fits the
utility-first component patterns generated by shadcn/ui, and supports modern CSS
features without a heavy custom build setup. The codebase already uses the
Tailwind CSS v4 PostCSS plugin in `postcss.config.mjs`, and ADR-0004 requires a
component foundation that is compatible with Tailwind CSS v4.

We also want styling decisions to be explicit in the ADR set rather than
implicitly bundled into the component-library choice.

Alternatives considered:

- **Tailwind CSS v3**: Mature, but requires the older configuration model and
  does not align with the v4 direction already assumed by the current setup.
- **CSS Modules**: Good for local scoping, but slower for composing a shared
  design language across utility-heavy components.
- **Vanilla CSS only**: Minimal tooling, but would add more handwritten styling
  overhead as the component library grows.

## Decision

Use **Tailwind CSS v4** as the project styling system, with the
`@tailwindcss/postcss` v4 plugin configured in `postcss.config.mjs`.

Tailwind CSS v4 matches the project’s component approach, keeps styling close
to markup, and supports shadcn/ui’s expected setup. The PostCSS integration is
the canonical build path for this repository.

## Consequences

### Positive

- Utility-first styling keeps component development fast and consistent.
- Tailwind CSS v4 aligns with the generated shadcn/ui component patterns used in
  the repository.
- The `@tailwindcss/postcss` plugin keeps the build configuration small and
  explicit.

### Negative

- Contributors need to understand Tailwind conventions to work efficiently in
  the UI layer.
- Tailwind major-version changes can require coordinated updates across styles,
  generated components, and tooling.

### Neutral

- Some global design decisions still live in CSS custom properties and app-level
  styles rather than in Tailwind utilities alone.
